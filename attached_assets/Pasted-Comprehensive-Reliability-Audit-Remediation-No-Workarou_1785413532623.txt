2. LID Resolution

The resolver contract explicitly states:

ResolvedTarget.jid must NEVER be a @lid.

Guarantee this contract.

When the matched participant is a LID:

- resolve it using the existing helper functions
- prefer bestRealJid(...)
- use resolveRealJidFromMeta(...) where appropriate

If the final value is still a LID:

- treat the participant as unresolved
- fail safely
- never fabricate an @s.whatsapp.net JID from LID digits
- never use LID digits as the displayed phone number
- never persist LID-derived numbers into ban lists, permit lists, or logs

Moderation actions must never execute against a LID.

3. Participant Resolution

resolveTarget() already identifies the participant.

Do not perform another participant search inside the moderation pipeline.

Use:

directly.

Delete duplicate participant lookup helpers that are no longer needed.

Audit every command accepting a target.

Support:

- Reply
- Mention
- Phone number

- International number

5. Removal API Validation

Audit removeParticipantWithRetry().

Do not assume success simply because groupParticipantsUpdate() resolved.

Inspect the returned participant status array.

Require:

status == 200

for the requested participant.

Treat every other status as failure.

Feed failures through the retry logic only when appropriate.

Retry only transient failures.

Do not retry permanent failures.

- JIDs

Retry only when justified.
